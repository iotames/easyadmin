# 关键架构决策

> 状态：综合建议，待 P0 评审。D13（API 不设路径版本、向下兼容）已由用户确认；其余决策仍待评审。确认后不得仅凭个人偏好改变；变更必须补充替代方案、成本、迁移和复审理由。

每条决策记录：结论、理由、代价、复审条件。

## D01 显式装配，不做自动扫描

**结论**：模块、Provider 和路由由 `cmd` 组合根显式登记；不以 `init()`、反射扫描、注解或目录约定自动装配。

**理由**：装配可读、依赖可追踪、缺失依赖可在启动前发现，符合 Go 惯用方式。

**代价**：新增模块需更新装配处。该显式成本可接受。

**复审**：不复审核心原则；具体装配 API 可以随验证调整。

## D02 SQL-first，不引入 ORM

**结论**：建表、索引、迁移和查询使用外置 `.sql` 文件；Go 代码进行参数绑定和结果映射，不引入 Active Record 或 ORM。

**理由**：SQL 可见、可审查、可优化；避免隐式查询与 N+1。

**代价**：手写 SQL 有重复。P5/P6 可选代码生成，但生成物必须可读、可编辑、可重复生成。

**复审**：不以 ORM 替代 SQL-first。

## D03 原生 ESM + 零构建为默认前端

**结论**：浏览器原生 ES Module、动态 `import()` 和 CSS 变量；生产资源通过 `go:embed` 交付。Node/npm/Vite/Webpack/Vue/React 不作为运行或默认构建前提。

**理由**：Go 一条命令启动、减少工具链和部署依赖、天然支持页面级懒加载。

**代价**：没有 JSX/SFC/TypeScript 编译；使用 JSDoc、显式 DOM 组件生命周期和浏览器测试管理复杂度。

**复审**：真实业务证明复杂交互成本过高时，只讨论可选开发增强；生产仍不得依赖 Node。

## D04 SQLite 默认，其他数据库逐一认证

**结论**：SQLite 为零配置默认数据源；PostgreSQL/MySQL 作为目标驱动，完成驱动、SQL 方言、事务、迁移和集成测试后才列为正式支持。

**理由**：默认开箱即用，同时不把“理论可接”当成“已支持”。

**代价**：需维护方言脚本和测试矩阵。

**复审**：P2 依据真实测试确定官方支持矩阵。

## D05 后端 Manifest 是菜单/权限/页面元信息权威来源

**结论**：菜单、权限、页面标识和模块依赖由 Go Manifest 显式声明；`/api/meta` 返回当前用户可见数据。前端维护 `Page ID → ESM loader` 静态映射，并由架构测试校验一一对应。

**理由**：避免菜单重复维护，服务端始终是权限权威。

**代价**：后端 Manifest 与前端 JS 入口仍有两个物理登记点，必须自动检查其一致性。

**复审**：不复审服务端权限权威；映射实现可优化。

## D06 默认服务端会话，不默认 JWT

**结论**：同源后台使用数据库会话 + HttpOnly Cookie + CSRF；不把 JWT/localStorage 当默认方案。

**理由**：便于即时登出、会话撤销与权限更新，适合管理后台。

**代价**：未来多实例必须使用共享会话存储。

**复审**：外部 API/移动端等出现明确需求时单独设计 Token Provider。

## D07 任务持久化，调度器只做触发

**结论**：Task Center 负责任务状态与执行；Scheduler 只负责到期判断并提交 Task。

**理由**：手动和定时任务使用同一入口，能取消、查询、接管和审计。

**代价**：需要任务表、日志表和保留策略。

**复审**：多实例阶段增加租约/抢占，不改变职责分离。

## D08 单实例优先，多实例独立设计

**结论**：v0.x/v1.0 以单实例为明确支持基线；不宣称当前任务、调度、SQLite、本地文件支持多实例。

**理由**：多实例需要完整解决锁、租约、共享会话和存储。

**代价**：高可用部署需等待后续独立阶段。

**复审**：出现真实需求时单独立项。

## D09 错误码稳定，文案面向用户

**结论**：业务错误使用稳定 Code；Message 说明发生了什么、原因及下一步；内部 Cause 只进日志。

**理由**：前端逻辑不依赖文案，用户能处理错误。

**代价**：需要治理错误码和文案。

**复审**：不复审。

## D10 v0.x 只做启动配置，运行设置后置

**结论**：v0.x 的配置中心只管理进程级启动配置（Bootstrap Config），由 easyconf 适配层负责来源与优先级。需要管理 UI 编辑、审计和版本控制的运行设置（Runtime Settings）作为后续扩展点，不在 v0.x 落地，也不允许数据库隐式覆盖启动配置。

**理由**：

- 启动配置与运行设置生命周期不同，混在一起会产生双真相；
- 运行设置需要额外的表、权限、审计、版本冲突和缓存失效设计；
- 先把启动配置做扎实，比提前造一个没有数据模型的 Settings Service 更可靠。

**代价**：业务运行期设置暂时只能通过业务模块自己的表实现，不能共用统一 Settings Service。

**复审**：出现明确的运行设置需求时，单独设计 `sys_setting` 表、读取优先级和 API，不在配置中心里偷偷扩展。

## D11 内置后台必须使用框架自身能力

**结论**：EasyAdmin 自带后台是框架第一个真实用户，不允许开后门。

**理由**：保证公开组件与业务项目真正可用。

**代价**：内核未成熟时后台开发会受影响。

**复审**：不复审。

## D12 模块之间不直接 import

**结论**：模块不直接 import 其他业务模块内部实现；跨模块依赖通过消费方窄接口和组合根显式注入。

**理由**：减少循环依赖，模块可替换和独立演进。

**代价**：需要定义小接口和装配代码。

**复审**：接口过多时先评估模块边界是否拆错，不先引入全局容器。

## D13 API 不设版本号，向下兼容

**结论**：所有正式 JSON API 统一挂载 `/api/`，不使用 `/v1`、`/v2` 路径版本；`/healthz`、`/readyz` 是明确例外。API 变更遵循“只增不改”：新增字段、端点、可选参数和枚举值可以；删除、重命名、改类型、改语义不可以。

**理由**：

- 管理后台与调用方共享一套稳定契约，避免版本分叉；
- 路径版本号容易被误当成“旧接口可以随便坏”，与向下兼容目标相反；
- Go 的静态类型和契约测试足以约束兼容性，不需要靠 URL 版本兜底。

**代价**：

- 需要维护兼容性测试与弃用流程；
- 设计新字段时必须考虑旧客户端；
- 真正无法兼容时只能新增端点或走重大决策，成本更高。

**复审**：不默认引入路径版本。若未来出现无法通过新增端点解决的兼容问题，单独立项评审。

## D14 `net/http` 是业务 HTTP 语义边界

**结论**：业务 handler 使用标准 `net/http` Handler；easyserver 的路由和服务生命周期由适配层封装。

**理由**：减少底层私有上下文扩散，保留 Go 标准生态互操作。

**代价**：必须在 P1 验证 easyserver 的 handler/context/timeout/shutdown 支持。

**复审**：若底层实际限制导致无法实现，先给出证据和最小替代方案。

## D15 首期不使用 Go `.so` 插件

**结论**：模块以编译期 Go 包和显式装配为主；不把 Go `plugin` 当作通用扩展系统。

**理由**：跨平台、版本和部署限制较多，与可预测交付目标不符。

**代价**：添加后端模块需重新构建发行产物。

**复审**：若真实需求需要进程隔离或第三方扩展，优先设计进程外 Provider 协议。

## D16 主键与时间口径统一

**结论**：核心关系表主键采用 `int64` 并与 API 数据结构一致；时间统一 UTC 存储，API 使用 RFC3339。

**理由**：透明、易查、跨 SQLite/MySQL/PostgreSQL 易于实现。

**代价**：公开 API 不直接暴露厂商特定类型；任务编号等外部标识另设字段。

**复审**：若分布式 ID 成为真实要求，再通过明确迁移决策升级。

## D17 Go 与依赖版本在 P0 冻结

**结论**：文档中的版本号先视为候选，不把“当前最新”写成长期约束。P0 检查 Go 工具链、easy 系列 API、驱动、许可证和安全状态后固定版本。

**理由**：避免规划文档过期或依赖不兼容。

**代价**：P0 必须做依赖核查记录。

**复审**：每次依赖升级按变更记录与测试矩阵执行。

## D18 目录命名：Go 习惯、明确语义、保留约定短名

**结论**：目录名要短、可指认、不与 Go 既有强语义冲突；同时承认约定俗成的短名有可读性和避让价值，不做机械的一刀切。

- 顶层采用：`cmd`、`kernel`、`infra`、`apps`、`webui`、`sql`、`templates`、`examples`、`lib`、`docs`。
- 能力包采用：`conf`、`logx`、`db`、`httpapi`、`apperror`、`auth`、`audit`、`tasks`、`scheduler`、`storage`。
- `platform` 指 `GOOS/GOARCH` 运行平台，不作为基础设施目录名；基础设施统一入口改用 `infra`。
- `modules` 与 Go module（`go.mod` 定义的依赖单元）冲突，业务目录改用 `apps`。
- `kernel/module` 是单数的 Module 契约包，职责唯一，保留；本条避免的是顶层 `modules/` 复数目录。
- `apps` 按业务域/限界上下文组织；域内按子域、用例或领域层划分，不按纯技术层平铺。
- `logx` 保留：比 `logging` 短、好记，并能与标准库 `log` 明确区分。
- `lib` 保留：语义明确为本地接入的 easy 系列/第三方代码，不承担 Go 包命名职责。
- `conf` 保留：比 `config` 短，且在配置语境中没有歧义。

**避免的万能词**：`common`、`util`、`base`、`helpers`、`misc`、`shared`，以及没有明确职责的 `core` 桶。

**避免的强语义词**：`platform`（`GOOS/GOARCH`）、`module`（`go.mod`）、`vendor`（Go 依赖目录）、`internal`（Go 可见性规则）。

**理由**：目录名是长期公共契约。短名降低调用成本，明确语义降低误读；对已经成为团队共识且无歧义的短名（`logx`、`lib`）保留，比为了“完整”而拉长更符合工程实际。

**代价**：`logx`、`lib` 与完整词命名不完全一致，需要在本文和 `PROJECT_STRUCTURE.md` 中明确其边界，避免后来者按个人偏好再次改名。

**复审**：命名原则不复审；新增顶层目录或能力包时，必须对照本条说明职责和命名理由。

## D19 业务项目依赖版本化框架，不复制基础设施

**结论**：

- `templates/app` 是唯一脚手架源；`examples/biz` 是唯一业务示例，不保留 `examples/minimal`。
- `easyadmin new` 只生成薄壳工程：`cmd`、`apps`、`webui`、`config`、`go.mod`；业务项目不复制 `kernel`、`infra` 和内置 `apps`。
- 业务项目只 import 公开包：`kernel`、`infra/*`、内置 `apps` 的构造函数、`webui` 契约；`infra/internal` 和框架内部实现不是公开 API。
- 升级通过 Go module 版本完成；核心迁移 scope 为 `core`，业务迁移 scope 为 `app:<module-id>`，互不改写。
- 业务定制优先用配置、构造函数选项、窄接口和追加注册；禁止 fork 内置模块或长期维护 vendor 补丁。
- 允许业务项目用 `git submodule` 固定 EasyAdmin 提交，并通过 `replace` 指向 `./lib/easyadmin`；submodule 必须指向官方仓库，不修改框架源码，框架改进须回流上游。

**理由**：只有保持单一框架实现，通用组件和基础设施的修复才能一次进入所有现有和未来项目；复制代码会把升级收益切断。

**代价**：必须严格维护公开 API、JS 契约和迁移兼容性，业务不能随意修改框架内部。

**复审**：公开包边界和版本策略在 P5/P6 复核；“不复制基础设施”的原则不复审。
