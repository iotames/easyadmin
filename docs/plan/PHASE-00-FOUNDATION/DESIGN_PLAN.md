# P00 设计计划：地基与工程规范

> 状态：PROPOSED（待用户评审；未批准前不得进入本期实施）。

## 1. OGSM：本期目标与衡量

**Objective（目的）**：把现有 EasyAdmin 仓库从“基础设施源码与规划文档并存”整理为边界清楚、依赖可复现、能够持续验证的工程基线。

**Goals（目标）**：
1. 现有实现、目标架构、尚未实现能力三者在文档中明确区分。
2. 建立可重复的 Go 构建、测试、静态检查与依赖检查入口。
3. 固化分层与组合根约束，建立能识别典型违规的自动化检查。
4. 建立最小启动/资源交付验证，不在 P0 偷跑身份、权限或业务数据能力。

**Strategies（策略）**：
- 先审源码和依赖，再确定规范；不把旧规划当作实现证据。
- 复用已有 infra 代码，按差距补齐，不重建同名基础设施。
- 把 easy 库调用方观察与底层库保证分开；未知项转为验证清单。
- 设计确认和开工授权分离；通过后才进入实施步骤。

**Measures（度量）**：
- 现状清单覆盖每个已存在 infra 包及其持久化状态。
- Go build/test/vet/race 在干净环境有可复现命令和结果。
- 架构测试覆盖依赖反向、底层库绕行、前端裸 fetch 等明确红线。
- 文档相对链接 0 个断链，计划配对 7/7。
- P0 不新增业务持久化表，不建立用户/角色/认证实现。

## 2. 现状结论（源码证据）

以下为当前仓库可直接核对的实现事实；目标目录不能当作已存在代码。

| 现状 | 源码证据 | 结论 |
|---|---|---|
| 配置管理已存在 | `infra/conf/interface.go`、`infra/conf/config.go` | 有 Manager、ConfigItem、Set、Watch、List；来源元数据/安全持久化写入仍须核验 |
| 数据库通用能力已存在 | `infra/db/` | 有 DDL/Catalog/Diff 等基础实现；不能等同于完整 migration runner |
| 命名数据源管理已存在 | `infra/db/datasource.go` | 当前是 JSON 文件仓储，不是 `sys_datasource` SQL 表 |
| 凭据与 SSH 能力已存在 | `infra/credential/credential.go` | AES-GCM、SSH 测试、别名与隧道能力已迁移；服务器管理 API/存储未实现 |
| 任务中心已存在 | `infra/tasks/taskcenter.go` | 当前纯内存；重启后任务状态丢失；终态只保留最近 500 条 |
| 调度核心已存在 | `infra/scheduler/scheduler.go` | 有 Store 接口与 MemoryStore；数据库 Store 未实现 |
| 地基库依赖已有版本记录 | `go.mod`、`go.sum`、`.gitmodules` | Go 与 easy 系列版本已有候选固定值；P0 应做可复现与兼容核验，不从空白选版本 |
| 运行时上层骨架尚未建立 | 当前树中无 `cmd/`、`kernel/`、`apps/`、`webui/`、`sql/` | P0 只建立经确认的最小骨架 |

当前基线依赖记录：go.mod 声明 Go 1.26.0，并以本地 lib 子模块/replace 接入 easy 系列。最终可复现性以实际 submodule commit、go list -m all、go mod verify 与干净环境构建结果为准。本轮只检查仓库文本和源码，不声称已运行 Go 测试。

## 3. 本期范围

- 统一 README、AGENTS、ARCHITECTURE、DECISIONS、ROADMAP、COMPONENTS、CONVENTIONS、FRONTEND、API、数据/配置/日志文档中的现状口径。
- 核验 Go、easy 系列和直接依赖的版本、来源、许可证与可复现接入方式。
- 固化 cmd 组合根、kernel/infra/apps/webui 依赖方向和禁止反向依赖规则。
- 定义公共组件设计检查约定，但不要求所有组件实现同一接口或生命周期。
- 定义 HTTP 解析/绑定、字段校验、领域规则、权限和状态冲突的责任边界。
- 建立 Go build/test/vet/race 的基础验证入口与架构测试。
- 建立 dev 磁盘读取和生产 embed 的最小资源交付骨架。
- 建立最小 App/HTTP 页面 smoke，只证明依赖装配、生命周期和资源交付贯通。

## 4. 明确不做

- 不创建用户/角色/权限/会话/审计等业务表，不实现登录和初始化管理员。
- 不建设 ORM、Runtime Settings、Task Center 持久化、Scheduler SQL Store、文件管理和系统信息页面。
- 不提前实现 P1 运行时完整内核、P3 完整后台 UI 或 P5 CLI。
- 不因为对标其他框架引入全局对象、反射扫描、自动注册、万能接口或不必要依赖。
- 不将文档中的目标树写成当前实现状态。

## 6. 数据结构与持久化边界

P0 不新建业务持久化表、不执行 schema migration、不创建默认管理员。最小 smoke 所需的临时状态只允许进程内存储；不得借由启动示例提前固定 P2/P4 的业务数据模型。

## 7. 交付与验收标准

| 验收项 | 验收方法 | 通过标准 |
|---|---|---|
| 现状准确 | 对照源码树与依赖清单 | 每项标明已实现/部分实现/未实现 |
| 依赖复现 | go mod verify、submodule status、干净环境构建 | 依赖来源明确，无未解释的本地漂移 |
| 工程反馈环 | go build、go test、go vet、适用的 race | 命令在 CI 与本地一致，失败能定位 |
| 资源双模式 | dev 模式磁盘资源、生产 embed 资源 | 两种模式均能访问最小页面 |
| 架构边界 | 自动化架构测试与故意违规样例 | 反向依赖和被禁用入口被测试捕获 |
| HTTP 输入边界 | 单测/集成测试与 API 契约 | 400/422/409/403 语义一致 |
| 文档一致性 | 相对链接、阶段配对、路径核查 | 无断链；7 期各有 DESIGN/IMPL 配对 |
| 交付边界 | 检查 sql 与业务表 | P0 未创建身份、审计、任务等业务表 |

截图只能作为浏览器验收辅助证据，不替代自动化测试。任何未实测的 easy 系列语义必须记录为 P1 验证项。

## 8. 风险与缓解

- **把现有 infra 当成完整产品能力**：逐包列出内存/文件/数据库边界；尤其不把任务中心/调度写成已持久化。
- **依赖版本已记录却重复选择**：先验证现有 pin 与 submodule commit，只有发现具体问题才提出调整。
- **配置写入破坏来源优先级**：P0 不实现在线写入；P1 必须区分生效、持久化与重启应用。
- **设计计划过早细化后期工程**：P1-P6 保持路线级约束，前置阶段验收后再按事实校准。

## 9. 质量自评

| 维度 | 自评结论 | 评审重点 |
|---|---|---|
| 工程化最佳实践 | 先固定依赖、模块边界、错误与生命周期契约，自动化守卫防止回退 | 测试/CI 是否覆盖真实失败路径，而非只验证目录存在 |
| 用户体验 | 只验证最小启动和静态页交付，不提前制作空壳业务页面 | 页面 smoke 是否真实可访问、错误是否可诊断 |
| 改动量与复杂度 | 复用现有 infra，避免 ORM、全局容器和重复基础设施 | 是否有为抽象而抽象、是否引入不必要依赖 |
| 架构统一性 | cmd 作为唯一组合根，infra 不认识 apps/webui，HTTP 采用统一适配边界 | 依赖方向测试能否捕获反向引用 |

以上为设计阶段自评，不是实施验收。
