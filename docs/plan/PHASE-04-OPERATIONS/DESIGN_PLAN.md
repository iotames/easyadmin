# P04 设计计划：运营能力

> 状态：`PROPOSED`（待用户评审；未批准前不得进入本期实施）。

## 1. 背景与目标

让框架支持长任务、调度、文件、系统日志和诊断。

## 2. 本期范围

- Task Center 持久化、状态机、进度、任务日志、取消、重试、接管和清理。
- Scheduler 到期扫描、跳过记账和统一 Task Submit。
- 本地 Storage、文件元数据、受控上传/下载/删除。
- Application/Access/Audit/Task 日志的查询边界。
- 任务、调度、日志、审计、文件、系统信息页面。

## 3. 明确不做

- 多实例分布式调度、集群选主和任务租约。
- S3/OSS 等厂商强依赖。
- 外部监控平台和完整日志分析系统。

## 4. 架构与契约决策

- Scheduler 只触发，不执行业务任务。
- 任务状态机/并发/重试语义明确。
- 运行日志查询有真实 reader 或索引来源。
- 文件存储与数据库元数据分离，下载受鉴权。

设计必须服从 `docs/ARCHITECTURE.md`、`docs/DECISIONS.md` 和 `docs/CONVENTIONS.md`。若本期需要改变其中任一正式边界，必须先提交 ADR/决策修订，不可在实施计划中暗改。

## 5. 交付与影响面

- `infra/tasks`、`scheduler`、`storage`。
- `sys_task`、`sys_task_log`、`sys_schedule`、`sys_file` 表和迁移。
- 系统运维模块 API/UI。
- `LOGGING_DESIGN.md` 和对应数据字典。

## 6. 验收标准

- 进程重启后遗留 running 任务能收口。
- 同一 schedule 上轮未结束按规则 skipped，不堆积。
- 任务取消和关闭有确定结果。
- 文件路径穿越、类型、大小、权限均有测试。
- 日志查询分页和保留策略有边界。

每项验收都必须对应可执行测试、命令、浏览器操作或源码核验记录。截图不能替代功能测试。

## 7. 风险与缓解

- 不在 handler 中直接起无人管理 goroutine。
- scheduler 不运行长任务。
- 不宣称当前多实例安全。
- 日志中心不得查询不存在的索引数据。
